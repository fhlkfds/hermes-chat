# Scheduled jobs are Hermes's cron jobs, managed over dashboard REST and confirmed by reading the list back

Scheduled jobs are the profile's own Hermes cron jobs. Hermes stores them in the profile's `cron/jobs.json`, and the gateway's scheduler runs them on the server, so they keep running while Hermes Chat is closed. The app reads and writes them only through dashboard REST `/api/cron/*` (`hermes_cli/web_routers/cron.py` at the deployed `bf0203a`): list, create, edit, pause, resume, run now and delete, plus the run history and the delivery targets. Every call names the profile. After every write, whatever Hermes answered, the app reads the profile's list back, and only that read decides whether the change worked.

## Considered options

- **Schedule from the app.** Rejected: jobs would run only while the app is open, and the server already has a scheduler with catch-up, at-most-once firing and per-profile locks.
- **Legacy `cron.manage` over `/api/ws`.** Rejected: it lists, adds, pauses, resumes and removes, but can't edit a job or read its runs. Dashboard REST can.
- **Trust Hermes's answers.** Rejected for the same reason as ADR 0005: a lost answer says nothing about whether the write committed, and Hermes's cron routes have no idempotency key and no revision.
- **Trust the per-job routes' `?profile=`.** Rejected: when the named profile doesn't hold the job id, Hermes acts on whichever profile does (`_job_owner_profile`, made for the official app's cross-profile list). Checked with a throwaway `HERMES_HOME`: resuming a second profile's job with `?profile=default` resumed it. So every action first checks that the profile's own list (`GET /api/cron/jobs?profile=…`, which is strictly scoped) holds the job, and refuses an answer stamped with another profile. That narrows the fallback to a job deleted in another client while a change is on its way, but can't close it; only a strict `?profile=` on Hermes's side would.

## Consequences

- **Copies.** Hermes copies a profile's `jobs.json` into a profile made from it, so the same job id is often in two profiles (9 of the deployed `default` profile's 10 jobs are also in `orchestrator`). The job screen names the profiles holding a copy and says what the fallback would do. A delete checks the copies afterwards and says plainly if Hermes deleted one, claiming so only when that profile's list was read and lacks it; pause, resume, edit and Run now find out from the profile stamped on Hermes's answer. Run history is read only for a job the profile's own list holds before and after the read, since a script run's rows name no profile, and refused if its rows name another profile.
- **Duplicates.** A second press of Create waits for the first. When a create's answer is lost, the app looks in the list for a new job with the same prompt, name and delivery. A list without it proves nothing, since Hermes may still be saving it after the connection dropped, so the next press of Create looks again and, if it still isn't there, warns instead of sending; only a further press sends it anew, and the warning says to delete one if both arrive. That memory lasts for the app run only.
- **Edits.** The editor sends only the fields the owner changed (and the repeat limit with a new schedule, since Hermes re-derives it when the schedule's kind changes), so fields it doesn't show (model, skills, script, folder, toolsets, chained jobs) stay as Hermes has them. Before sending, it compares the job's shown fields with the copy the owner opened; if another client changed one, nothing is sent until the owner saves again over it or reloads. A change landing between that check and the write can still be overwritten: Hermes offers nothing to close that gap. When the answer to an edit is lost, a schedule counts as saved only if the job now has the schedule asked for, by Hermes's own label and its expression, interval or instant (a time without an offset read in the profile's zone).
- **Time zone.** Hermes schedules a profile's jobs in its `timezone` setting (read from `GET /api/config`), else in the server's own zone, which it doesn't name; the app then shows the offset Hermes stamped on the profile's jobs and says that daylight-saving changes can't be previewed. A cron schedule follows the zone's wall clock. The editor's explanation and upcoming runs mirror `parse_schedule` and `compute_next_run`, checked against Hermes's own code with the clock pinned (`tools/cron-golden.py`): a wall time skipped when clocks go forward runs by the old clock (02:30 runs at 03:30 the new time) and later skipped times don't run; a time that happens twice runs only the first time; an interval counts elapsed time. Hermes's own `next_run_at` is always the next run shown. The scheduler checks about once a minute, so a run can start up to a minute after its time.
- **Run now** calls `POST /api/cron/jobs/{id}/trigger`, which Hermes answers only once the run has finished, so the app says the run finished, with Hermes's recorded status, only when `last_run_at` moved, and only shows the job as the list has it afterwards: a job gone from the list (a one-shot Hermes removed) leaves it, and a list it couldn't read is said to be unconfirmed. It is a real run, with the job's real delivery, and Hermes also resumes a paused job; the app asks first and says so.
- **Runs.** `GET /api/cron/jobs/{id}/runs` lists agent sessions and script output, newest first. It takes a limit (at most 100) and no offset, so the app pages by asking again for 20 more of the newest, up to 100, and then says older runs aren't listed. Since each page is the newest N read afresh, a run that arrives meanwhile shifts the rows rather than repeating one. It answers 503 until the profile's gateway has started its session store; the app says so.
- **Run states** come only from what Hermes recorded (checked on a throwaway `bf0203a` home, 2026-11-04). A script run's row is titled with the execution ledger's status (`COMPLETED · …`, `FAILED · <error>`), or with the job's `last_status` when no output survived (`OK`, `ERROR`, `DELIVERY FAILED`, …). An agent run's session carries `end_reason`: `cron_complete` when its last row is a real reply, `cron_incomplete_no_output` when the turn died first (`cron/scheduler.py`). A run is running while `scheduler_owned` (a live scheduler holds its ledger claim) or still active. Anything else is unknown, with why: a session never closed that no live scheduler owns (its process died), a run compressed into a session Hermes doesn't list, an output with no ledger record, or a status this app doesn't know. The app never guesses success from a missing error.
- **Results.** Agent runs aren't opened as chats: Hermes's `cron` sessions are left out of the chat list, and opening one would offer to send into it. **Show the result** reads the run's session over `GET /api/sessions/{id}/messages?profile=&order=latest&limit=50` and shows the newest assistant text, read-only. That route opens only the named profile's store (a `fixture-b` read of a `default` run answered 404) and stamps `profile`, which the app checks. Its newest page is in stored order, oldest row first, so the reply is the replying row with the highest id. A script run shows what Hermes previews of its output (180 characters); the whole output is only on the server, in the profile's `cron/output/<job id>/`.
- **Profiles.** New job can create the job in any profile the server lists (`GET /api/profiles`), with that profile's time zone, catch-up setting and delivery targets read first; the job then shows in that profile, not this one's list. An edited job stays in its profile: Hermes has no move, and a delete plus a create would be a new job with new run history and a second chance to run twice.
- **Summary and delivery.** Before saving, the editor sums the job up (profile, schedule in words on its time zone, when it stops, where it delivers, whether it starts paused) beside its next runs. It sends nothing to try a delivery: the first delivery is the job's first real run. The screen says when Hermes can't deliver a job where it says, mirroring `_resolve_single_delivery_target` against `cron_delivery_targets`: a platform not set up on the profile's gateway, a bare platform with no home channel (unless the job came from that platform), or a Bot Chat profile that doesn't exist. `local`, `origin` and `all` are never flagged, since Hermes resolves or falls back for them on the server. When the targets can't be read, nothing is flagged and the screen says it couldn't check.
- **Late answers.** Every read on the screen is sequenced: the job list, each job's history and copies, a run's result (kept by run id), and the editor's read of another profile's settings. An answer a newer read superseded, or that arrives after the screen, job or profile changed, is dropped. The screen is keyed on the profile, so a profile switch starts it again.
- **Missed runs.** The job screen says what Hermes does with a run its scheduler missed (`_compute_grace_seconds`, `_fast_forward_missed_recurring`): a recurring run up to half its period late (2 minutes to 2 hours) still runs; later, the missed runs become one run, or none when the profile's `cron.catch_up_missed` (read from `GET /api/config`) is off; a one-shot more than 2 minutes late doesn't run.
- **Scheduler health.** Each job carries `scheduler_heartbeat_age_s`. The app warns when it is missing (no scheduler has run for the profile) or over five minutes old, since jobs run only while the profile's gateway runs.
- **Relay.** The Rust relay takes `POST api/cron/jobs`, `PUT api/cron/jobs/{id}` and `POST api/cron/jobs/{id}/{pause,resume,trigger}`, with the id one plain path segment, and no other new `POST` or `PUT`.
- **Overlapping runs.** Hermes runs one execution of a job at a time: a Run now while one is under way is answered 409 (checked live: a second trigger of a 45 s script four seconds into the first). The app shows a job whose ledger has a claimed or running execution as Running, says so in the Run now confirmation, and words the 409 as "running already". Two rows can show as running at once, when a manual run was claimed while a scheduled one went on.
- The app offers only Hermes's delivery targets (`GET /api/cron/delivery-targets`), marking a platform with no home channel; a job's current target it doesn't list is kept. It creates prompt jobs only; script jobs and other options come from other Hermes clients and are shown as kept.

- **Troubleshoot** hands a job to Hermes in a new chat in its profile, and shows what changed once the reply ends: ADR 0051.

## Capability gaps, and the server changes that would close them

None of these is worked around with a local store or timer; the screen says what it can't show.

- **History past 100 runs.** The runs route takes `limit` (capped at 100) but no offset or cursor, though `SessionDB.list_cron_job_runs` already takes `offset`. An offset over the merged list would skip or repeat rows as runs arrive, since sessions, output docs and ledger rows are reconciled per request. Design: `GET /api/cron/jobs/{id}/runs?profile=P&limit=N&before=<started_at>:<id>`, applying the keyset after `_reconcile_cron_runs` (rows strictly older than the cursor, by `started_at` then `id`), and answering `next_cursor` from the last row, null at the end. The app would then ask for 20 at a time with the cursor instead of the newest N.
- **A script run's whole output.** Only `_cron_output_run_preview`'s 180 characters are served. Design: `GET /api/cron/jobs/{id}/runs/{run_id}/output?profile=P`, resolving a `cron_output:` id to its doc under the owner's `cron/output/<job id>/`, size-capped, with the same profile scoping as the runs route.
- **The outcome of a compressed agent run, and an agent run's ledger error.** The runs route lists a run's first session only, and an agent session row carries no ledger status. Design: stamp `execution_status` and `execution_error` from `cron/executions.db` on each session row that names its `cron_execution_id` (the route already reads the ledger for script runs), so every run carries the scheduler's own completed, failed or unknown.
- **Strict `?profile=` on per-job routes,** **an idempotency key on create** (`request_id`, stored with the job, a repeat answering with the first job) and **a revision on update** (`expected_updated_at`, 409 on a mismatch) would close the races described above.
