# Work planning reads links per task, writes them one at a time, and leaves Decompose out

> **Accepted.** Issue #604, first PR. The Graph view (`src/ui/WorkGraph.tsx`, `src/hermes/workGraph.ts`), the sheet's links, bot and model pickers and token guess, and the Dispatch line (`src/ui/WorkPlan.tsx`) are on the Work page (ADR 0171). Their reads and writes are `KanbanApi` methods in `src/hermes/kanban.ts`.

The owner wants to plan work for several bots from the Work page: see which cards wait on which, change that, pick each card's bot and model before it runs, and get a rough idea of its size. Hermes's kanban plugin has the routes for each (`plugins/kanban/dashboard/plugin_api.py`, the same file at `b200f5bc`, `bf0203a` and `f0d9488`). It also has Decompose, which splits a triage card into linked cards. The issue's goal for Decompose is that nothing runs until the owner says so, and Hermes can't promise that today.

## Decisions

- **The graph is drawn from each linked card's own read.** No route lists a board's links. `GET board` gives each card's `link_counts`, and `GET tasks/{id}` gives a card's `links` (parents and children, by id) and `link_tasks` (their titles and statuses). The page reads only cards whose counts are above zero, and keeps each read until that card's counts or status change on the board. Adding or removing a link changes both ends' counts, so it shows at once. A link swapped for another elsewhere keeps the counts, so it shows only after Refresh, which drops every read. A link to a task that isn't on the board, such as an archived one, ends at a dashed ghost card named from `link_tasks`, or by its id when Hermes no longer has it.
- **The layout is computed, not dragged.** Each card goes one layer past the furthest card it waits on, parents at the left, and each layer is ordered once by where its cards' parents sit. Cards with no links are listed apart under the graph, as "Not linked". Hermes refuses a loop, but a loop the reads show anyway goes in a last layer instead of hanging the layout.
- **Every write in the sheet is previewed, refused if the card changed, sent once and read back** (ADR 0014, ADR 0171). Each section has one state: idle, confirming, writing, unconfirmed or failed. The confirm says what the change does. Removing a todo card's last open parent says that Hermes makes it ready at once (`recompute_ready`) and the dispatcher starts it on its next tick if it has a bot or the server sets `kanban.default_assignee`. For a blocked card it says the card stays blocked if someone blocked it, and may go ready and start if Hermes blocked it itself after failed runs: `recompute_ready` lifts a block it made but not one a person or a worker made, and only the task's events tell them apart. That warning is worked out again from the read taken just before sending: if a parent finished in the meantime and the card would now start, nothing is sent and the new confirm shows. Adding a parent to a ready card says it goes back to todo. Giving a ready card a bot says the dispatcher starts it on its next tick. Just before sending, the sheet reads the task again. If its links, bot, model or status differ from what the sheet showed, nothing is sent and the sheet shows what is there now. After sending, it reads the task until the change shows, with the section locked. A lost answer keeps it locked with Try again, which can't do the change twice: adding a link that exists adds no row, removing one that is gone writes nothing, and setting a bot or model sets the same value.
- **A model is set with its provider, or cleared.** Hermes clears the provider when a model is sent without one, so a model from the catalog (`GET model-options`) always goes with its provider, a typed model goes alone, and "Bot's default model" sends `clear_model_override`. When Hermes can't build the catalog it answers an empty list, and the sheet takes a typed model.
- **An estimate is a token guess, never a cost.** Hermes's own code calls `POST estimate` "NOT a dollar cost". The page shows "Token guess: about N tokens, size M", the model's reason, and "A model's rough guess of tokens, not a cost." It writes nothing, so it can be asked again at any time.
- **The Dispatch line says what the server does on its own, never that it waits for the owner.** It reads `GET orchestration` when the page opens and on Refresh: whether Hermes splits triage cards (`kanban.auto_decompose`), whether a split's cards that wait on no open card are made ready at once (`kanban.auto_promote_children`), and always that a ready card with a bot starts on the dispatcher's next tick, every 60 s by default, while the server's gateway runs it. The route doesn't say whether a dispatcher runs or its interval, so the line says "by default". Diagnostics shows the same two settings and the profile's `kanban.review_dispatch`, read from `GET /api/config`.
- **Each part has its own capability** (`workDispatch`, `workPickers`, `workLinks`, `workEstimate`) and hides only when Hermes lacks its own route. The kanban capability no longer guards `links` and `estimate`, so an older plugin without one of them still shows the board. Links and estimates have no read to check them by, so Diagnostics sends a link from a task to itself, which Hermes refuses before it reads the board, and an estimate with no title, which Hermes answers without asking a model (ADR 0169).
- **Decompose is left out.** Hermes writes the cards Decompose makes at once, and its dispatcher promotes every todo card whose parents are done and starts every ready card with a bot on its next tick, even with `auto_promote_children` off. A Plan box would let the first cards run within a minute, before the owner could edit them. It waits for one of two things: a Hermes plan preview and hold (`decompose {dry_run: true}`, `decompose/apply {hold}`, and a per-card hold the dispatcher skips), or an app-side hold that links every new card under a blocked gate card the app makes first, once a throwaway Hermes shows the dispatcher never starts them.

## Considered options

- **Read every task's detail for the graph.** Most cards have no links, and the board already counts them, so only linked cards are read.
- **Re-read every linked card on each 10-second board poll.** That is one request per linked card every 10 seconds while the page is open. Reading again only when counts or status change, and on Refresh, misses only a link swapped for another with the same counts.
- **A graph library.** The layered layout is a short pure function with tests. A library would add a dependency for a few dozen cards.
- **An app-side hold for Decompose now.** It depends on the dispatcher never starting a card under a blocked gate, which no throwaway Hermes has shown yet. Saying "nothing runs until you say so" on a server that would start the cards is the failure the issue forbids.

## Consequences

- The Graph view reads one task per linked card when it opens, then only cards whose links or status change, and all of them again on Refresh.
- A link swapped for another elsewhere with the same counts shows on the next Refresh.
- The relay now takes `POST api/plugins/kanban/links` with exactly `parent_id` and `child_id`, `POST api/plugins/kanban/estimate` with a `title` and an optional `body`, and `POST api/plugins/kanban/tasks/{id}/estimate` with no body (`kanban_write`). `DELETE links` and the picker `PATCH`es were already relayed.
- Diagnostics sends two more write checks while it is open. Neither changes anything or asks a model.
