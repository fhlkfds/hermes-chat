# Everywhere search reads every profile of every live connection through the shared read slots

> **Accepted and built (issue #608, first PR).** It amends ADR 0125: a background connection now answers one kind of search read, and the four slots that bound its background reads also bound every Everywhere read. The fan-out is `searchEverywhere` in `src/hermes/everywhere.ts`. The slots are `LiveConnections.readInTurn` in `src/hermes/liveConnections.ts`. The per-profile read is `Hermes.searchIn` in `src/hermes/transport.ts`. Opening a row is `openAt` in `src/App.tsx`. The scope is in `src/ui/Search.tsx`.

The owner can't always remember which bot they talked something over with, or on which server. Search (Ctrl+K) looked in the profile on screen only, so finding the conversation took one search per profile on each connection, with a profile switch or a target switch between them. Issue #608 asks for one search over every bot's chats.

Hermes has no search across profiles. `GET /api/sessions/search` searches one profile's store for each request, gives at most 100 chats with one hit each, and takes no date, model or offset. A hit names the chat and not the message. So the app asks each profile itself and merges the answers.

## Decisions

- **Everywhere is a scope of the search palette.** A switch beside the words picks **This profile** or **Everywhere**. The words carry across. Everywhere needs words: it never lists chats, because listing every profile on every server is a different cost.
- **Each profile is asked once, with Hermes's own search.** For each live connection that is connected, the app reads `GET /api/profiles`, then sends one `GET /api/sessions/search?q=&profile=&limit=100` for each profile. Archived chats and Bot Chats are left out, as Search leaves them out today. To know the Bot Chats' ids, the app reads each connection's roster (`profiles.list`) once before that connection's searches.
- **Every one of those reads takes one of four slots.** ADR 0125 lets at most 4 background reads run at once across the background connections. That limiter is now `LiveConnections.readInTurn`, and the background reads and every Everywhere read share it. So at most four requests are in flight across the live connections, whether they come from one search, from two searches that overlap, or from a search and the background reads. Each read is one request, so the slots in use and the requests in flight are the same number.
- **A freed slot goes straight to the read that waited.** The limiter used to give up its slot and wake the waiting read, which took the slot back a moment later. A read asked for in between got in as well, and five ran. A profile listing that answers and queues its searches hits exactly that moment. The slot now passes to the waiter without being freed.
- **A background connection answers these reads, and still runs no search of its own.** ADR 0125 says a background connection never searches. `Hermes.searchPage` and `browse` still refuse there, because their results go in the shown list. `Hermes.searchIn` is a different read: one dashboard GET that names its profile, touches no session, and puts nothing in any list. It returns a `Hit`, which is a `Found` without `settled`, so the type keeps a background connection's result out of `reveal` and out of a pane.
- **Rows arrive as each profile answers.** A search keeps one map of slots: each connection is waiting, offline, refused, failed or listed, and each profile of a listed connection is waiting, searched or failed. One function works out what the palette shows from that map, for a partial outcome and for the whole one. A server that is slow holds back its own rows only.
- **Rows are grouped, not ranked.** The composer target's rows come first, then each other connection's in the order they opened. Within a connection the profiles are in Hermes's order, and within a profile the chats are in the order Hermes's search gave. Hermes ranks within one profile only, and its scores aren't comparable across stores. Each row names its server and its bot above the snippet.
- **The Bot filter decides which profiles are asked.** It is text matched against the profile's name, so it needs no list of profiles before the first search. A profile it leaves out gets no request.
- **Model and dates are checked here, after Hermes has picked its 100.** Hermes's search can't narrow by either. The palette says so in a note whenever one is set. The dates mean last active, as they do in This profile (`checkedHere` in `src/hermes/chatFilter.ts` is the one definition). A chat with no model recorded is counted and left out, as in This profile.
- **A profile that hits the cap says so.** When a profile answers 100 chats, the note names the bot and the server, and says more chats may match there.
- **A server with no chat search is left out, with why.** The `chatSearch` capability checks the route with a blank `q`, which Hermes answers with `{"results": []}` before it reads its store. A Hermes older than the route reads `search` as a chat's id and answers 404 "Session not found", as `GET /api/sessions/{id}` does. That answer used to read as "the route is there". A capability can now name the answers of a neighbouring route that show its own is missing (`missing` in `src/hermes/capabilities.ts`). Once a connection's capability is unsupported, none of its profiles is asked, a profile that was waiting for a slot is never sent, and the next search sends that connection nothing. A refusal of another kind, such as a 403 or a 500, is that profile's failure and is shown with Hermes's reason.
- **A stopped search sends nothing more.** A new filter, or leaving the scope, stops the search. Its requests that were waiting for a slot are never sent. The relay can't cancel a request already sent, so those finish and are dropped, and they hold their slots until they do.
- **Opening a row uses the path chat links use.** `openAt` makes the row's connection the composer target if it isn't, and `Main` opens the chat through the link job (ADR 0037): it looks the chat up, asks before it leaves a profile with work under way, switches profile, and opens. This covers a row in the profile on screen, a row in another profile, and a row on a background connection. The job then sets the pane's picked search result, so find-in-chat goes to the words the row matched, as it does for a result picked in This profile. The lookup also reads whether the chat is Settled, which the search row doesn't say.
- **Tags, Source, State, Save filter and Tag results stay in This profile.** Tags and Saved filters are kept for one connection and profile (ADR 0106). Everywhere shows none of them.

## Consequences

- An Everywhere search can wait behind the background reads, and they behind it. The app has one number for reads at once across connections.
- Opening a row in the profile on screen costs two short reads (`GET /api/profiles` and `GET /api/sessions/{id}`) and a brief notice. In exchange, the three cases share one tested path, and a chat deleted since the search says so.
- Everywhere rows show no Settled badge and no Tags. A badge would cost a second request for each profile.
- A connection that isn't connected is named as not searched. Nothing is sent to it.
- The first search on a connection reads that connection's roster, and a roster read also asks for each bot's picture once (`profiles.get_asset`), as opening the Bots view does. Those picture reads go over the socket and are not in the four slots. A background connection makes them too.
- A search costs one `GET /api/profiles` for each connection each time it runs. The app keeps no list of profiles between searches, so a new profile is searched at once.

## Not decided here

- Bot Chats are left out, as Search leaves them out today. The owner's question, which bot they talked something over with, may be about exactly those chats. Showing them means opening one through the Bots view, not the link job.
- The issue names both `started_at` and `last_active` for the date filter. This ADR checks last active only, so the dates mean the same in both scopes.
- The scope is not remembered between openings of the palette. Each opens in This profile.
- The other parts of issue #608 (Tool used and File touched filters, Ask, the memory review queue, the local index) are later PRs.
