# Skills are Hermes's own skill routes, checked first and read back

Settings → Skills lists, switches and edits the skills Hermes offers the model in the profile shown, through the dashboard's own skill routes (`hermes_cli/web_routers/skills.py`). At the deployed `bf0203a` they are `GET /api/skills?profile=` to list, `PUT /api/skills/toggle?profile=` `{name, enabled}` to turn one on or off, and `GET`/`PUT /api/skills/content` to read and replace a skill's SKILL.md. They are the same at `f0d9488`, which only adds a `locked` flag to the list and a `PUT /api/skills/lock` route. This app uses neither. Every call names its profile in the query, and Hermes scopes the skills folders and config to it (`_profile_scope`), so unlike Memory (ADR 0020) every profile's skills can be managed. Hermes has a skill registry and resources over REST, so nothing is read from this computer's skill folders, and nothing goes around Hermes to the server's files.

## Decisions

- **What a skill is here.** The list is `find_all_skills` for the profile: its own `skills/` folder, `skills.create_dir` and `skills.external_dirs`. Each row shows its name, description, category, source (`provenance`: `agent` shows as Local, `bundled` as Built in, `hub` as Skills Hub, `external` as External folder), its scope, and whether it's on. Scope is Shared for a skill in an `external_dirs` folder, since other profiles may list that folder, and This profile otherwise. Plugin skills aren't in that list, and aren't shown. Search filters the rows on this computer, by name, description and category.
- **On and off.** The switch is Hermes's own toggle, which adds the name to the profile's `skills.disabled` or takes it off, under the config lock. A change is said to have worked only once the list read back shows it. A lost answer or a 5xx is settled by that read. A 4xx is a refusal that changed nothing. `hermes-agent` is essential: Hermes keeps it on whatever the config says, so it has no switch. `skills.disabled` is every platform's list. Hermes also has per-platform lists (`skills.platform_disabled.<platform>`), and this app's chats run as `tui`, or `desktop` on a dashboard started with `HERMES_DESKTOP`. The screen reads those two lists from `GET /api/config`, keeps nothing else of the config, and marks a skill they keep off as Off in this app's chats. Hermes matches an entry against a skill's declared name or its list name (`is_disabled_entry`). The list name is the declared name unless two skills declare the same one; then each is listed by its path, such as `writing/one`. So when an entry names no listed skill, the screen reads the SKILL.md of each skill listed by a path, to learn the name it declares. If one of those reads fails, the screen says it can't be sure which skills the lists keep off. The switch can't change those lists, and says so.
- **File identity.** The editor shows the server, the profile, and the path Hermes reports for SKILL.md. Hermes looks a name up by folder name first, then `category/name`, then front matter `name:` (`_find_skill`). So a folder named like another skill's name would hand back the other skill's file. When the file read names a different skill that is also listed, the editor refuses to open it and says why, so a save can't land on the wrong skill.
- **Validation before saving.** The front matter checks follow `_validate_frontmatter` and `_validate_content_size`: content not empty, a `---` block that is closed, `name:` and `description:` fields, a description of at most 1,024 characters, a body after the block, and at most 100,000 characters in all. On top of those, the name can't change (chats and `skills.disabled` know the skill by it), and merge markers left in the text block a save. The name is compared with the one the file declared when opened, not the list name, which may be a path. This app reads front matter only as plain `key: value` lines, taking the last of a repeated key as PyYAML does. A name it can't read for certain blocks the save, and a file with such a name isn't opened. That covers a block scalar, a value continued over lines, an escape in a double-quoted value, an anchor or flow value. It also covers front matter with a tagged, anchored, aliased, merged, complex or escaped key, or a flow mapping, since such a key could spell `name` another way. Hermes's own YAML parse has the last word: its 400 is shown as Hermes words it, and the edit stays. The files the body names are found the way Hermes's linter finds them (`references/…`, `templates/…`, `assets/…`, without globs or bare folders), and checked in the skill's folder through the managed-files listing, `GET /api/files` (ADR 0012). A path with `..` in it is never saved. A missing file stops the save until the owner chooses Save with missing files, since Hermes itself accepts it and the file may come later. A folder the listing can't reach (`HERMES_DASHBOARD_FILES_ROOT` elsewhere) is said to be unchecked, and doesn't block.
- **Save = check, write, read back.** Hermes has no revision for SKILL.md, so a Save first reads it again and writes only if the path and text are still what the editor opened, as Persona does (ADR 0014). It then reads the file back and says Saved only when Hermes has exactly what was sent. A lost answer, a 5xx or a deadline (30 s for reads, 60 s for the write) is settled by that read: the old text means it wasn't saved, and the edit stays. If the read-back fails too, the app says it can't tell. The next Save checks first, and finds the text already there if it was saved.
- **Conflicts keep both versions.** When the file changed on the server, nothing is written. The owner's edit stays in the editor, and the server's version is shown beside it, read-only, with Copy. **Merge into my edit** runs the same line-based three-way merge as Server file edits (ADR 0024) from the file as opened. Lines both sides changed are kept between markers, which must be settled before the next save. **Use the server's version** drops the edit, after asking. A change that lands during the save, found by the read-back, is offered the same way.
- **Restore previous version.** Each save from here keeps the text it replaced, up to ten per skill, in memory for the sign-in. Restore puts the latest one that differs back in the editor as an unsaved edit, to save through the same checks. Nothing is kept on this computer or the server.
- **The edit can't be lost by accident.** Cancel, All skills and Restore ask before dropping an unsaved edit. So do leaving Settings, changing tab, opening a chat, switching profile, signing out and closing the window, which use the Memory screen's question (ADR 0020). Only one save or reload runs at a time. A late answer for a skill or profile no longer on screen is dropped.
- **Skill text is data.** It is the agent's instructions from wherever the skill came from. The screen shows it only as text nodes and in a textarea. It is never rendered as Markdown or HTML, and nothing in it is run.
- **What reaches the server.** The Rust relay passes only `PUT api/skills/toggle` with exactly `{"name", "enabled": bool}` and `PUT api/skills/content` with exactly `{"name", "content": string}`, the profile in the query (`skill_write_allowed`). A name must be one line of at most 256 characters, with no backslash, no leading `/`, and no empty, `.` or `..` segment. The webview refuses the same names before sending. Creating a skill (`POST /api/skills`), `PUT /api/skills/lock`, and every Skills Hub route (install, uninstall, update) aren't relayed. Installing skills from elsewhere fetches and runs code from outside, and is a separate step.

## When changes take effect

`skill_view` reads SKILL.md from disk each time the agent loads a skill, so a saved edit reaches the next load, in any chat, including one already going. The route clears Hermes's skills index cache, so the name and description reach chats started afterwards. A chat already going keeps the index its system prompt started with. `skill_view` checks `skills.disabled` on every call. So turning a skill off keeps it out of new chats' index, and makes Hermes refuse to load it in any chat from then on. Turning one on lists it in new chats, and a chat already going can load it by name. Nothing is restarted or reloaded. Hermes's `skills.reload` rescans skill slash commands and leaves the prompt cache alone. This app doesn't call it. The composer runs skills through `command.dispatch` (ADR 0015), which reads SKILL.md when the message goes, so a saved edit reaches the next run. A switch or a save here makes the composer read its list of skills again. Hermes's discovery list caches a scan for up to 30 seconds and can't see an edit made inside a file, so the list's description can lag a saved edit by that long. The editor's read-back reads the file itself, and switches are never stale, since the disabled list is part of the cache key.

## Considered options

- **Edit through Server files (`/api/files/upload-stream`, ADR 0024).** Rejected: it skips Hermes's front matter and size checks and its opt-in security scan, writes the file `0600`, and doesn't clear the skills index cache.
- **The legacy socket's `skills.manage`.** Rejected: it lists and installs, but doesn't edit or switch.
- **Reading this computer's `~/.agents` or `~/.hermes/skills`.** Rejected: the skills that count are the server's, for the profile shown.
- **Keep earlier versions on this computer.** Rejected for now: a skill can hold anything the agent or a hub wrote, and the app has no business keeping copies of the server's files (as ADR 0024). The versions last for the sign-in.

## Consequences

- **The check-then-write gap.** Hermes has no conditional write for SKILL.md, so a change that lands between the check and the write is overwritten, and the read-back then reports a save. The backend fix is an `expected_sha256` (or `If-Match`) on `PUT /api/skills/content`, compared with the file under the skill's mutation lock right before the atomic write. Toggles have the same gap per name. A change to another skill is never lost, since each write names one skill.
- **Line ends and BOM.** Hermes reads SKILL.md with universal newlines and `utf-8-sig`, so the editor can't see a file's CRLF line ends or byte order mark, and a save writes LF without one. Unknown front matter fields and the rest of the text are kept as they are, since the whole text is sent back as edited.
- **Only SKILL.md.** A skill's other files aren't edited here; Server files can upload one. Skills can't be created, renamed or deleted here.
- **Bundled and hub skills.** Editing one makes Hermes's updates (`hermes update`, `hermes skills update`) keep the owner's copy and stop updating it. The editor says so.
- **Shared skills.** An edit to a skill in an `external_dirs` folder reaches every profile that lists it. The editor says so. A folder Hermes can't write (a read-only mount) fails with Hermes's error, shown as a refusal, and the edit stays.
- **Newer servers' rules.** From `f0d9488`, Hermes refuses an edit that changes the description to more than its skill-index width. The screen doesn't check that ahead of time, since `bf0203a` allows it. Hermes's refusal is shown, and the edit stays.
- **Verification limits.** The tests use a fake of these routes (`fakeSkills.ts`), and the Rust relay is tested against a stub. The real routes were exercised against a throwaway dashboard from the deployed checkout (`docs/screenshots/skills/README.md`). Unsupported servers are recognized by their 404 or 405 for the routes. A server whose answers have another shape is said to be one this app doesn't understand.
