# A job run opens as a read-only chat, read from its stored rows

> **Accepted.** Replaces the **Results** consequence of ADR 0013. The chat kinds and what each may do are in `src/hermes/chatKind.ts`, the stored read in `src/hermes/storedTranscript.ts` and `Hermes.open` (`src/hermes/transport.ts`), and the run's button in `src/ui/ScheduledJobs.tsx`.

The owner wants to read what a scheduled job did on a run: the prompt it got, each tool call and the reply, not only the last reply. Each run of an agent job is a Hermes session with source `cron` (ADR 0013). Until now the app kept those sessions out of every list and showed a run's last reply only, through **Show the result**. ADR 0013 gave the reason: opening a run as a chat would offer to send into it.

That risk was already real. Usage → **Open this chat** lists sessions from every source, and it opened a run as an ordinary chat, with the composer, Edit, Regenerate and Branch. Hermes v0.23.1 refuses any message typed into a run (`cron_session_read_only`, `gateway/session_cron.py`) and stores the refusal in the run's transcript, so one try leaves a failed turn in the job's record.

## Decisions

- **A Job-run chat is its own kind of chat.** `chatKind` names four kinds: ordinary, Imported transcript, Bot Chat and Job-run chat. One table (`CHAT_POLICY`) says for each kind whether it is in the chat list, whether it can make Inbox entries, how it opens, which note replaces the composer, and whether Edit, Regenerate, Branch, Pin, Settle, Archive and Delete apply. The app reads the kind from the session's source: a `cron` session is a Job-run chat wherever it comes from. Every gate reads the table, so a new kind of chat must answer every question before it compiles.
- **A Job-run chat is read, never resumed.** Opening one reads its stored rows over dashboard REST, `GET /api/sessions/{id}/messages`, oldest first, 500 rows a page, with the turns compaction took out of what the model reads (`include_compacted=true`), as `session.resume` and Hermes's own desktop app read them. Hermes answers such a read as one display history, without the copies compaction keeps. The Run view reads a run's replies the same way. The app never sends `session.resume`, so no live session starts. It never sends `PATCH /api/sessions/{id}`, so the run is never marked read. Hermes opens its store read-only for that route. The app also reads `GET /api/sessions/{id}` for the run's title and its job (`cron_job_id`). The transcript is read again on every open and no Saved copy is kept, so a run can't be read while Hermes is out of reach.
- **The app turns the stored rows into a transcript itself.** `session.resume` returns rows that Hermes has already shaped for display (`_history_to_messages`, `tui_gateway/session_history.py`). The REST route returns the raw rows. `projectStored` mirrors the parts of Hermes's projection a run uses. It leaves out hidden rows and `[System:` notices, shows a compaction summary row by the `display_content` Hermes gives it, and names each tool row from the assistant's call, as Hermes does. It keeps every tool's output, where Hermes keeps only the edit tools' output to keep a resume small. The rows are read whole anyway, and a run's tool output is the record of what it did. Hermes's compaction and commentary projections aren't mirrored, since a run doesn't compact or hold commentary. The run's first message shows as Hermes stored it, the job's prompt after Hermes's own instructions for a scheduled run.
- **Nothing can send into a run.** The composer is replaced by a note saying the chat is a run of a scheduled job and Hermes won't take a reply. When the job is known, the note has **Open the job**. Edit, Regenerate, Branch, the queue, voice, model and context controls, Pin, Settle, Archive and Delete are gone. The Run view, Find, Export, Share snapshot and Copy chat link stay, since they only read. The header shows **Job run** where an ordinary chat shows **Settled**. In the transport, `resume`, `send` and the chat-changing actions refuse a Job-run chat, so a path that bypasses the screen can't reach Hermes either.
- **Runs stay out of the chat list, unread counts and the Inbox.** Every list and search call still sends `exclude_sources=cron`. A run that is open is kept in the app's chats so that its pane can show it, but the kind table leaves it out of the list, the unread counts, the window title, the Saved list, the chat reopened at launch and the Inbox. The Inbox also leaves out a live session whose source is `cron`. Bot Chats keep their Inbox entries (ADR 0066).
- **Search and Saved filters can ask for runs.** The Source filter has **Scheduled jobs**. Only a filter that asks for it drops `exclude_sources=cron` and sends `sources=cron`. **Other platforms** still leaves runs out. Hermes titles a run only when it ends. Until then the app calls it by its job's name, or "Scheduled job run" where the job isn't known, and its start time, never by its first message.
- **Each agent run in a job's history opens its chat.** **Open the chat** sits beside **Show the result**, which stays as the quick look. A script run has no session and no chat.

## Considered options

- **Resume the run over `/api/ws` and hide the composer.** `session.resume` is safe on a run: it asks only to read, and Hermes keeps an ended run ended. But it starts a live session and runs plugins' `on_session_open` hooks. A run is a record, and reading it shouldn't start anything.
- **Keep runs out of the app's chats and show them on a screen of their own.** Leaving a run out of the list would then follow from where it is kept, not from a table. But the screen would need its own transcript view, or a chat view with a dozen do-nothing handlers. It would also lose tabs, split panes and the Run view, and a run would look unlike every other chat. The kind table gives the same exclusion with one rule per question.
- **A flag on the chat, as Bot Chats have.** That adds a second boolean beside `bot` that every check must remember. Bot Chats already show the cost: the Inbox reads every chat, so each new exclusion would be one more condition someone has to add there.

## Consequences

- The kind table also carries the Imported transcript and Bot Chat rules that were scattered checks before, with the same behaviour.
- Usage → **Open this chat** and chat links now open a run read-only.
- A list saved by an earlier version holds a run it opened as another platform's chat. Until the list is read on a connection, opening such a chat waits for the read. The read drops it, and the pane then finds the run by its id as a Job-run chat. Until the read succeeds, the chat shows its Saved copy and nothing is marked read or resumed.
- A run's transcript shows only what Hermes stored. Hermes answers the messages of a compressed run's whole lineage from its first session's id, so a run's chat is whole even when the runs list names only that first session (ADR 0013).
- `projectStored` can drift from Hermes's own projection when Hermes changes it. The difference shows as a row shaped differently from a resumed chat, never as a write.

## Follow-up: replying in a run

Replying in a run needs a Hermes change, so it is left out. Hermes admits a message typed into a run and then refuses it, because the run's session only runs its job (`gateway/session_cron.py`). A reply would need Hermes to carry a run on in a new session of its own, a branch that takes the run's history and runs as an ordinary chat. The app would then offer **Reply in a new chat** in place of the note. Until Hermes offers that, the owner starts a new chat, and can use Troubleshoot (ADR 0053) to hand Hermes the job.
