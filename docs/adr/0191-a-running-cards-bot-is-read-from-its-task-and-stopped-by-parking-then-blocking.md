# A running card's bot is read from its task, and stopped by parking the card, then blocking it

> **Accepted.** Issue #604, part 4b. A card's sheet on the Work page (ADR 0171) shows its Task run and offers Stop, Reclaim and Reassign (`src/ui/WorkRun.tsx`). The reads and the one write method are in `src/hermes/kanban.ts`. The plan each write follows is in `src/hermes/taskRuns.ts`.

The owner wants to see what a running card's bot is doing and what it has used, and to stop it, run it again or give the card to another bot. Before this, the Work page showed a running card as a title in the Running column. The only control was the footer's Block, which leaves the bot working. Hermes has no write that stops a run and blocks its card in one step, and no kanban write except `POST tasks` takes an idempotency key. Every fact below was checked on a throwaway Hermes `bf0203a` with its dispatcher running. The answers it gave are in `src/hermes/kanbanRunsGolden.json`.

## Decisions

- **A card's runs come from the read the sheet already makes.** `GET tasks/{id}` answers `runs` and `events`. A Task run is a run with a `claimed` event, or with a worker pid on a Hermes that sends no events. Blocking or completing a card writes a run row too, with no `claimed` event and one time for both ends. Those rows are dropped when the task is read, so no code later asks whether a run is a real one. A row's `profile` doesn't tell the two apart. A run's heartbeat is the later of its `last_heartbeat_at` and its newest `heartbeat` event. Its chat is the `session_id` of its `owner_admitted` event.
- **The bot's chat is read under the run's profile.** `GET api/sessions/{id}?profile=` gives the tokens so far and a message count, which grow after each model call. The last rows are read (`messages?order=latest&limit=6`) only when the count moves, and shown as three lines at most. While the sheet is open and a run is live, the section reads the card and the chat every 5 seconds, timed from the end of the last read. It skips a read while the window is hidden or its own write is on its way. Its reads never hold the board's 10-second poll, and they stop when the sheet closes.
- **Each action is one order, carried out as read, plan one write, send, read again.** `plan(order, read)` is a pure function that answers the next write or how the order ended. It holds the whole policy: refuse when the card changed, read back, and what to do after a partial write. `KanbanApi.changeRun` is the only public way to send these writes. A write is never sent twice in one call. A lost answer ends the call, and Try again starts from a fresh read, so it sends only what Hermes doesn't show yet.
- **Nothing is sent when the card isn't as the confirm showed it.** Before the first write, the card must be running, its live run must be the run the confirm named, and its bot must be the same.
- **Stop parks the card, blocks it, then gives it back.** The writes are `POST tasks/{id}/reassign {profile: "", reclaim_first: true}`, the page's own block (`PATCH {status: "blocked", block_reason}` and its `BLOCKED:` comment), and `PATCH {assignee}`. Parking stops the bot and leaves the card ready with no bot, so the dispatcher has nothing to start it with. Terminate then block was the other order. It leaves the card ready with its bot between the two writes, and a lost answer on the block puts the bot back to work on the next tick. Block then terminate fails: Hermes answers 409 "already ended" and the bot works on.
- **Stop chases a run the dispatcher starts in a gap, and names one it can't stop.** A server that sets `kanban.default_assignee` gives a parked card to that profile and starts it. If a read shows a newer live run, Stop parks the card again, which stops that run too. If the dispatcher claims the card between the last read and the block, the block ends that run's row and leaves its bot working, and Hermes has no route that stops it then. The read back finds it as a Task run newer than the confirmed one that ended `blocked`. The sheet names that run, says its bot works on to the end of its turn, and says the card stays blocked. The confirm says which case applies, from the configured `default_assignee` in `GET orchestration`. `resolved_default_assignee` names a profile even when none is configured, and the dispatcher doesn't use it.
- **A reviewer's run is left in Review with no bot.** Stopping it puts the card back in review, and Hermes refuses a block from there. Stop ends there and says so. It doesn't give the bot back, because that would start the review again.
- **Reclaim stops the run the owner saw.** It sends `POST runs/{id}/terminate`. The card goes back to ready, or to review, and the dispatcher starts it again on its next tick.
- **Reassign always stops the run first.** It sends `POST tasks/{id}/reassign {profile, reclaim_first: true}`, the only form Hermes takes for a running card. The picker lists the board's bots except the current one. It has no "Unassigned", because leaving a card with no bot for good is Stop.
- **A running card has no moves while Hermes has the reassign route.** Hermes treats the moves differently: blocking a running card leaves its bot working, while a move to ready, todo or triage ends the run (`_set_status_direct`, `plugin_api.py:742` at `bf0203a`), and from ready the dispatcher starts it again. Stop, Reclaim and Reassign each say what they do, so they replace the moves. One function, `manualMoves`, decides the moves for both the sheet's footer and dragging on the board. On a plugin without the reassign route the moves stay, and the Block prompt says the bot works on.
- **Each write route has its own capability.** `workReclaim` guards `runs/{id}/terminate`, and `workReassign` guards `tasks/{id}/reassign`, which Stop and Reassign both need. Hermes added the two routes in different releases, so one capability would hide a working Reassign. Diagnostics checks each with a write that changes nothing (ADR 0169): a stop for run 0, which no card has, and a reassign of a card that doesn't exist. The kanban capability's write guard is built in code from every part's own routes.
- **A run that ended `blocked` isn't called stopped.** Blocking a running card ends the run's row and leaves its bot working. The section says that under such a run.

## Left out

- **`GET workers/active`, `GET runs/{id}/inspect` and the task's log.** The issue's checklist names them. All three describe the submitter, the process that waits for the bot. `inspect` reports that process's CPU and memory, and the log holds one `Session:` line until the run ends. Showing them as the bot would claim something Hermes doesn't say. The task read already has every run, and only its events name the bot's chat.
- **`POST tasks/{id}/reclaim`.** It does what terminate does, for whatever run the card has. Terminate names the run, so a run started since the confirm is never stopped by mistake. The relay refuses the route.
- **Open chat.** A session with source `kanban` lists as an ordinary chat today, with a composer onto a bot's live session, and a stored read reads only the shown profile. Opening a run's chat read-only needs a chat kind of its own, as a Job run has (ADR 0184). That is a separate issue.
- **Cost.** The session row's cost needs the usage screen's labels. The goal names tokens.

## Considered options

- **Each write in the section's own click handler, as the planning sections do.** One write fits there. Stop's three writes, the chase and the partial failures would be untestable without React, and Reclaim and Reassign would each repeat the read, refuse, send and read frame.
- **A wait and a second read when a read right after a write doesn't show it.** The links section does that. Here the call ends as unsettled, and Try again reads first. It needs no timer, and the same rule covers a refused write and a stale read.
- **One `workWorkers` capability.** It hides a working Reassign on a plugin that has only that route.

## Consequences

- While a running card's sheet is open, the app sends up to three small reads every 5 seconds: the task, the bot's session and, when the bot wrote, its last rows.
- Stop sends three writes, and one more for each run the dispatcher starts in a gap, up to five. Past five it stops and says where the card stands.
- Reclaim and Stop answer "this card changed" when the run the owner saw ended and another started. The owner confirms again against the new run.
- The relay takes `POST api/plugins/kanban/runs/{id}/terminate`, with no fields or only a `reason`, and `POST api/plugins/kanban/tasks/{id}/reassign`, with a `profile`, `reclaim_first` and an optional `reason` (`kanban_write`).
- Diagnostics sends two more write checks while it is open. It lists its write checks from the checks themselves.
- A Hermes change that stopped a run and blocked its card in one write would remove the chase and the race.
