# Troubleshoot hands a job to Hermes in a new chat, and the Jobs screen shows what changed

The Scheduled jobs screen (ADR 0013) has a **Troubleshoot** button on each job (in the list and on the job) and on each failed run. It hands the job to Hermes: a new chat starts in the job's profile, and its first message carries what the screen already reads. Hermes finds the cause and changes the job with its own cron tool (`cronjob` with `action="update"`, `tools/cronjob_tools.py` at the deployed `bf0203a`). The agent's tool works on the profile's own `HERMES_HOME`, so the chat must run in the job's profile. Hermes Chat changes nothing on the job itself. When the chat's reply ends, the screen reads the job again, lists what changed since the chat started, and offers **Run now** to check the fix.

## Decisions

- **The message is built from the screen's own reads.** It uses the job list, `GET /api/cron/jobs/{id}/runs` (the newest 5, plus the run the owner pressed it on when that one is older), each agent run's reply over `GET /api/sessions/{id}/messages`, and the delivery targets. These are the same routes, profile checks and parsing as ADR 0013, and there is no new endpoint. The job is read again just before, so the message and the "before" copy are the job as it is now. A history or reply that can't be read is said in the message, not left out silently.
- **What it carries:** the name, id, profile, schedule (Hermes's label, and in words), the schedule time zone (or that Hermes doesn't name one), whether the job is paused, finished or in error, the next and last runs, the repeat limit, the delivery target, the last error and delivery error, the model, skills, toolsets and folder when set, and the prompt or script. A script's text is only on the server, so the message names the script and says so. Each run shows its state, times, error, note and output: a script run's output is the 180-character preview Hermes serves (ADR 0013), and an agent run's output is its last reply. The message also lists the problems the screen flags: each delivery problem from `deliveryProblems`, delivery that couldn't be checked, and a scheduler with no heartbeat or one over five minutes old.
- **What Hermes is asked.** It must work only on this job in this profile. It must not create, delete or run jobs, since a run is real and delivers for real, and the owner runs it from the app. It says what it will change before changing it, and ends with every change, old and new value, or "nothing changed". When the cause is outside the job, it says what the owner must do. Text that was cut or hidden is unchanged on the server: Hermes reads it with its tool and never writes a marker back.
- **Long text is cut in the middle**, keeping the start and the end, since the cause of an error is often at the end of the output: 4,000 characters for the prompt, 1,200 for each error, output or reply. The cut says how many characters went, and the preview lists what was cut.
- **Secrets.** Every text from the server goes through `redact`: the prompt, errors, output and replies, and also names, the paused reason, model, skills, toolsets, folder and ids, the support bundle's patterns from ADR 0033 (`0033-logs-follow-hermess-log-tail-and-redact-before-keeping.md`): private keys, authorization and cookie headers, bearer tokens, URL credentials, JWTs, common provider keys, bot tokens, base64 key lines and `key=value` secrets. The preview names each kind it hid. These patterns don't catch a password in plain prose, a secret in a shape they don't know, or anything in a script's text (which isn't sent). **So nothing is sent until the owner has seen the message.** Troubleshoot opens a preview with the whole message in an editable box, and only **Start the chat** sends it, exactly as shown.
- **The new chat uses the existing new-chat path.** It is `Hermes.newChat()` and then `Hermes.send()`, the same calls as the composer's New chat. It is refused, with nothing sent, when the app no longer shows the job's profile. If the profile changes while the chat starts, the chat is left empty and the message isn't sent. The chat runs on the profile's own model, with no project, folder or hidden instructions: everything the model reads is in the one visible message. The chat opens in the active pane and stays an ordinary chat in the list.
- **"Done" is the end of the chat's reply.** A small in-memory store (`TroubleshootStore`) keeps, for this app run, the newest troubleshooting of each job by connection and profile. It holds the chat's id and the job as it was before. It watches the chat store and marks the troubleshooting ended once the chat, in the job's profile, while connected and attached on this connection (it has a runtime session), has no reply running. A dropped connection clears both the chat's runtime session and its running flag, so neither the drop nor the moment after the reconnect, before the chat is resumed, counts as an end. The resume sets both again from Hermes, and a reply that finished during the drop ends then. A first message whose acknowledgement was lost is followed the same way, marked as unconfirmed, since Hermes may have it and be changing the job. A chat that is never resumed (for example after a profile switch) stays "working"; the panel then offers **Read the job again**. When it ends, the Jobs screen (if open) reads the list again without the owner pressing Refresh, and the job's runs too. If the Jobs screen isn't open, a toast says so for 15 seconds, with **See what changed**, which opens the screen on the job. The screen reads everything fresh when it opens.
- **What changed is shown on the screen**, from the job as it was before against the list as Hermes has it now, and only from a list read that started after the reply ended. Until one has, the panel says it is reading the job again; if the read fails, it says why and offers **Try again**, and Run now isn't offered. While Hermes works, a read since the chat started shows the changes so far, marked as such. Each field that differs is listed with its old and new value: name, schedule (by its expression, interval or instant, since a one-shot moved to another time keeps Hermes's label), paused or not, prompt (before and after in full), script, agent or script-only, delivery, repeat, model, skills, toolsets, folder and chained jobs. Otherwise the screen says nothing changed. The comparison is against the list, never against what Hermes said in the chat. The job's row in the list says that troubleshooting is under way, or how many changes it made. **Run now to check the fix** opens the usual Run now confirmation (ADR 0013). The chat shows Hermes's own account and its tool calls.

## Considered options

- **Send without a preview.** Rejected: the message carries prompts, errors and output, and pattern redaction can't promise to catch every secret. One more click is the price of seeing what goes.
- **Put the instructions in a hidden first message** (`newChat`'s `instructions`, ADR 0017). Rejected: the owner should see everything the model is told.
- **Prefill the New chat composer and let the owner send it.** Rejected: the app couldn't link the chat to the job before it existed. The project and folder defaults of whatever pane was showing would also apply.
- **Have the app apply Hermes's fix itself** (Hermes proposes, the app writes it over `PUT /api/cron/jobs/{id}`). Rejected for now: the issue asks for Hermes to fix the job with its own tools, and the read-back still shows every change.
- **Keep troubleshooting records on disk.** Rejected: the "before" copy is only needed for the comparison right after the chat. After a restart, the chat itself still says what Hermes changed.

## Consequences and limits

- A chat that isn't resumed after a reconnect or profile switch isn't followed: its troubleshooting stays "working" until the owner presses Read the job again. Approvals inside the chat keep the reply running, so they don't end it.
- Changes made to the job by another client while the chat runs show as changes too, since only before and after are compared.
- A script run's whole output isn't served by Hermes (ADR 0013's gap), so only its preview goes in the message. Hermes can read the output files on the server.
- If Hermes deletes the job, the job leaves the list, and the screen says so as it does for any delete elsewhere.
