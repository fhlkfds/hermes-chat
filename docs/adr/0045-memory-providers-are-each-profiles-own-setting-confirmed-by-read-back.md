# Memory providers are each profile's own setting, written through Hermes's routes and confirmed by read-back

Settings → Memory edits a profile's built-in memory (ADR 0020). Every profile on the deployed server also uses an external memory provider, Honcho, and the owner wants to see which profile uses which, set each one up, and decide which profiles share memory. Hermes at the deployed `f0d94882e8` (v0.22.6) has dashboard routes for all of it, scoped by `?profile=` (research doc "Memory providers"). So the Memory tab gains an External memory section that reads and writes through those routes, for any profile, not only the one the app shows.

## Decision

- **What is shown.** A table of every profile (`GET /api/profiles`) with its provider (`GET /api/memory?profile=` → `active`, "Built-in only" when empty) and Hermes's status for it. Below it, one profile at a time, picked from the table and starting on the app's profile: "Built-in only" and each provider Hermes finds *for that profile*, with its description, status and what it needs installed. Opening a provider shows its settings.
- **Which settings surface.** The declared surface (`?surface=declared`, from the provider's `config_schema.py`) when it has fields, else the legacy one (`get_config_schema()`). Honcho's legacy surface has two fields and reads its key as unset when the key sits in the profile's host block, so it is never used when the declared one answers. Main settings show first; the rest under More settings, by Hermes's own groups. Secrets are write-only: Hermes says only whether one is set, a typed one is sent once and never kept, and a blank one is never sent.
- **Which profiles share memory.** Hermes doesn't link profiles: each names its provider, and the provider's settings pick the store. For Honcho the app knows what does: server (base URL, else environment), workspace, AI peer and user peer, a blank workspace or AI peer meaning the profile's own host, which the declared surface shows as the placeholder. The table shows those for each Honcho profile and names the profiles with all of them equal as on the same store ("Same store as …"). It doesn't claim more: those profiles share memory only if they also use the same Honcho account, whose key Hermes never sends back, and a `baseUrl` in a profile's own host block, which Honcho prefers but the dashboard doesn't report, would point it elsewhere. For other providers it says only that the settings decide (`STORES` in `memoryProviders.ts`; add one when it's in use).
- **Settings shared by a whole file.** Honcho keeps `baseUrl`, `timeout` and `sessions` at the root of `honcho.json` (`scope="root"`), and profiles without a file of their own read the default profile's. So a change to one of them reaches every profile on that file. Those fields are badged "All profiles on this file", and a change says so under the field.
- **Sharing is done by copying.** "Copy settings from another profile" fills the open form with the settings of a profile on the same provider, so both point at the same store, a blank that means the source's own host taking that host. Secrets aren't copied, as Hermes never sends them back: the screen says to type the key. Nothing is written until Save.
- **Writes.**
  - **Use for <profile>** with no changed settings: `PUT /api/memory/provider {provider}` ("" for built-in only), which Hermes refuses for a provider that isn't ready. Offered only for a ready one.
  - **Save and use for <profile>**: `PUT /api/memory/providers/{name}/config {values}` with only the settings the owner changed and any secret typed. Hermes's route also makes it the profile's provider, so the button says so. An empty write is never sent: the declared route would switch the provider without its readiness check.
  - **Install on the server**: `POST …/setup {values: {}}`, only after a question listing what Hermes will run (`hermes pm install` for Python packages, and each external dependency's own shell command, such as ByteRover's `curl … | sh`). It never carries settings. Each step's result and output is shown; `restart_required` is said as "restart Hermes there before chats can use them".
- **Checked first, confirmed by read-back.** As ADR 0021: one write at a time for the app; before a write the provider in use, and each changed setting, is read again and nothing is sent if it changed since the owner saw it (a save also switches the provider, so it mustn't undo a switch made elsewhere). Before an install, what the provider needs is read again and nothing is run if it differs from what the owner confirmed, since Hermes reads the manifest again when it runs. A copy is measured against the target's settings read again at that moment. A setting hidden by a legacy `when` isn't sent. After any answer, including an error, the profile's status and settings are read back. Saved is said only when both show what was sent. The legacy route writes before it refuses a provider that isn't ready, so a 400 can still have written: the screen says "Hermes saved the settings but didn't switch", and nothing is left marked unsaved. A lost answer whose change doesn't read back says it may yet land.
- **Relay.** Rust relays only these writes (`memory_provider_write`): `PUT api/memory/provider` with exactly a `provider` string that is "" or a Hermes provider name, `PUT api/memory/providers/<name>/config` with exactly `values` of string to string, never empty (an empty declared write would still switch the provider, unchecked), and `POST api/memory/providers/<name>/setup` with exactly `values: {}`. `POST api/memory/reset`, which deletes the built-in files, isn't reached.
- **Unsaved changes.** Provider settings count as the Memory tab's unsaved edit (ADR 0020's guard): leaving Settings, switching profile and the rest ask first, and switching the managed profile or provider inside the section asks too. They are never stored.
- **When it takes effect.** Hermes resolves the provider when it builds a chat's agent, so the screen says chats started after a change use it and a chat already going keeps its own. Saving restarts nothing.

## Considered options

- **Only the profile the app shows.** Rejected: the owner asked to see and set every profile, and these routes, unlike `learning.*`, take `?profile=`.
- **Edit `honcho.json` or config.yaml through the file routes.** Rejected: no lock, no precondition, and secrets would pass through the webview and back. Hermes's routes hold the config mutation lock and Honcho's token refresh locks.
- **A "share with" switch that links two profiles.** Rejected: Hermes has no such link, so the app would have to keep one and re-apply it. Copying shows exactly which settings change and leaves Hermes's config the only truth.
- **Installing catalog plugins (Mem0, Hindsight, …) from here.** Not now. Hermes's install route (`POST /api/dashboard/agent-plugins/install`) installs into the serving profile only, behind a consent and scan flow this app would have to show in full. The screen says to run `hermes -p <profile> plugins install <name>` on the server, then Reload.

## Consequences

- Any profile's provider can be read, switched, configured and installed from the app. What is shown as sharing is exact for Honcho and not claimed for other providers.
- A save switches the provider too, as Hermes's routes do. A provider can't be configured from here while the profile keeps using another.
- Installing runs the provider manifest's own commands on the server as Hermes's user, after the owner has read them.
