# The Screen adds a browser, a terminal and a text editor itself

> **Accepted.** The table of apps and the setup are in `src/hermes/screenApps.ts`, the note in `src/ui/Screen.tsx`, the Hermes calls in `src/hermes/transport.ts` (`ScreenApi.installBrowser`, `findPrograms`, `resetDock`, `stop`), and the install over ssh in `src-tauri/src/screen_apps.rs` with its script `screen_apps.sh`. Copy and paste with the screen is in `src/hermes/screenClipboard.ts`, `ScreenApi.readClipboard`, and this computer's clipboard in `src-tauri/src/clipboard_text.rs`. It partly supersedes ADR 0039 and ADR 0078.

The owner opens the Screen tab (Hermes's Bot Desktop, ADR 0039) and wants a web browser, a terminal and a text editor in its dock, with nothing to install by hand. On most servers the browser and the editor were missing, and the app only showed a command to copy for the browser (ADR 0078). Every Hermes fact below was read in its source at `bf0203a`, the owner's server.

- Hermes's launcher writes the dock once, when `<HERMES_HOME>/bot-desktop/xdg/xfce4/xfconf/xfce-perchannel-xml/xfce4-panel.xml` doesn't exist, with a launcher only for each program on the PATH then: `xfce4-terminal`, Hermes's own Chromium, `thunar` and `mousepad` (`tools/bot_desktop/launcher.sh`). A dock written before an app was installed never shows it.
- Hermes's desktop install includes `xfce4-terminal` but never `mousepad` or a browser. On Linux Hermes runs only pm's Chromium (`hermes_cli/browser_runtime.py`). `hermes pm install chromium` needs no root, and pm's store serves every profile.
- `cli.exec {argv, timeout}` runs `hermes <argv>` and answers `{blocked, hint?, code, output}`, for up to 600 s. `shell.exec {command}` runs a command as the Hermes user for up to 30 s, and refuses one its danger check flags. `display.stop` refuses while a person holds the screen, unless `force` is sent.

## Decisions

- **One table of the apps.** `SCREEN_APPS` names each one, how it is installed, and whether the dock has a place for it: `pm` for the browser, `system` with its program for the terminal (`xfce4-terminal`), the editor (`mousepad`) and `xclip`, which copying out of the screen needs (see below). `xclip` has no place in the dock, so adding it alone never deletes the dock's layout or offers a restart. The note's words and the check come from the table. A test checks that `screen_apps.sh` installs exactly the table's system programs.
- **It runs by itself, once per profile and connection.** The first time the tab is shown on a screen that is Hermes's own (not in the terminal's sandbox, which brings its own browser), supported and installed, the app checks and installs what is missing with no click. The browser is missing when `browserOf` says so. The system apps are checked with one `shell.exec` of `command -v xfce4-terminal; command -v mousepad; command -v xclip`. Debian's `sh` (dash) answers `command -v` only for the first name it is given, so each program gets its own. A Hermes without `shell.exec` skips them without a word, and nothing counts on them. The browser and the system apps install at the same time.
- **Hermes installs the browser.** `cli.exec {argv: ["pm", "install", "chromium"], timeout: 600}`, then `display.status` again: the browser is added once Hermes finds it. The app waits 660 s for that answer, longer than the run Hermes allows. If it fails, the note about no browser shows as before, with the reason first, and its command to copy and Check again.
- **The owner's own ssh installs the terminal and the editor.** They need root, and no Hermes route installs `mousepad`. The app runs one fixed script, `screen_apps.sh`, through ssh to the Terminal's target, as the Repository screen reaches the server (ADR 0110). The script picks apt-get, dnf or pacman, runs the install as root if ssh signs in as root, through `sudo -n` if sudo needs no password, and otherwise exits 10. The note then asks for the sudo password in a masked field. The password goes on ssh's stdin, which `sudo -S` reads. It is never an argument, never logged and never kept. The field is cleared as the install starts. A wrong password asks again. The script is constant and has no single quote, so the remote command is `exec sh -c '<script>' highwing-screen-apps <ask|password>`, one line.
- **Rust names how it ended.** Installed, needs a password, wrong password, no package manager, no sudo, failed (with the package manager's last lines), or an error before the script's end was known (ssh's own failure, in the Repository screen's words, or 15 minutes with no answer). The webview turns each into its sentence.
- **No SSH target, a command to paste.** The same script, as one line under `sudo sh -c`, read from the same file, so the two can't drift. Check again counts what the owner installed since as added.
- **The dock is written again only while the screen is stopped.** After something is added, the app deletes the dock's layout file with `shell.exec rm -f -- '<file>'`, and the screen's next start writes it with the new apps. The file is found from `display.status`'s `profile_key`, the profile's resolved Hermes home, so no extra `cli.exec` asks for it. A running screen's Xfce could write the old file back as it stops, so a running screen is left alone. The note offers Restart the screen: `display.stop` (never forced), delete the file, `display.start`. The app never restarts it on its own, since the agent may be in the middle of something there.

## Copy and paste with the screen

The owner wants to copy and paste between this computer and the screen, both ways. Hermes runs Xvnc with `-SendCutText=0 -MaxCutText 262144` (`launcher.sh`): the screen sends its clipboard to no viewer, and takes a viewer's. Hermes's bridge passes a client cut text only from the lease's holder, and drops the whole stream on one over 256 KiB (`tools/bot_desktop/rfb_filter.py`).

- **On focus, as desktop VNC viewers do it.** No key is caught. Only while the owner holds the screen: when the screen gains the focus or the pointer, this computer's text goes in through noVNC's `clipboardPasteFrom`, and Ctrl+V on the screen pastes it. When the pointer or the focus leaves, the screen's text comes out onto this computer's clipboard. Each way moves only text that changed since the last text that crossed either way, so what came out isn't pasted straight back. Paste here and Copy out in the Screen's bar do the same on a press and say what happened; the automatic moves are silent. Text only, up to 255 KiB of UTF-8, which leaves room for noVNC's framing under Hermes's 256 KiB.
- **Xvnc keeps pasted text only while the viewer that sent it is connected** (measured with Xtigervnc 1.15 and Hermes's flags), so the text goes in on focus rather than once, and a new stream sends it again.
- **Out, through xclip on the server.** `shell.exec` runs `DISPLAY='<display>' XAUTHORITY='<HERMES_HOME>/bot-desktop/Xauthority' xclip -selection clipboard -o`, with `display` from `display.status` and `<HERMES_HOME>` its `profile_key`, both quoted for the shell. `shell.exec` keeps only the last 4000 characters a command prints and masks what looks like a credential (`tui_gateway/methods_tools.py`), which would cut a long copy and change a copied key or token. So the command pipes xclip through `tail -c`, `head -c 1967`, `od -An -v -tx1` and `tr`: each call prints 1967 bytes as lowercase hex, which no mask matches, and the app asks for the next chunk until one is short. Each call reads the clipboard again, so it first prints the `sha256sum` of the whole clipboard on its own line, and the app gives up, saying the screen's clipboard changed while copying, when that hash differs between chunks. Text going in waits for a copy out under way, since pasting changes the screen's clipboard. xclip's "target STRING not available" is an empty clipboard. Hermes's danger check passes the command. Copy out shows, and the screen's text comes out, only when the apps check found `xclip` or added it, and `display.status` names the display.
- **This computer's clipboard through Rust.** In the app, WebKitGTK refuses `navigator.clipboard.readText()` with NotAllowedError even during a real key press, and `writeText()` outside one, and the text comes out after a `shell.exec`. So `clipboard_text` and `set_clipboard_text` read and write GTK's clipboard on the main thread. They don't use `gtk_clipboard_request_targets`, which `gtk_clipboard.rs` replaces. Elsewhere than Linux they answer that it works only on Linux for now.

## The agent's pointer

The owner wants to see the agent's pointer move on the screen. Nothing is built for it in the app, because the app's viewer isn't what hides it.

- **Xvnc already draws a pointer that something else moved.** With real noVNC 1.7, watching through Hermes's filter, and real Xtigervnc 1.15 with Hermes's flags, an XTest pointer move sends rects at the old and new pointer positions whether or not noVNC asks for the pointer's shape (the VMware and RFB cursor pseudo-encodings). Leaving those out changes nothing for the agent's pointer, and loses noVNC drawing the owner's own pointer with no delay.
- **Hermes's computer use doesn't move the X pointer by default.** Its input is "background-first": it is routed to the target window "without stealing the user's cursor or focus" (`tools/computer_use/schema.py`), and its cursor overlay is off on X11 unless `computer_use.no_overlay: false` is set (`tools/computer_use/cua_backend.py`). Showing the agent's pointer is Hermes's to do, with that setting.

## Sign-ins on the screen's browser

Hermes keeps one Chromium profile per Hermes profile, `<HERMES_HOME>/bot-desktop/browser-profile` (`tools/bot_desktop/browser.py`), used by the dock's Browser and the agent's browser. A sign-in there lasts across stopping and starting the screen, as measured with Chromium 145 from `hermes pm install chromium`: Chromium writes cookies to disk on a timer of about 30 s, and a stop sends TERM to the whole screen. A sign-in made in the last half minute before a stop may be lost, so Restart the screen says so next to its button: it is the one place this app stops a screen. Nothing here touches the browser's profile: the dock's reset deletes only `xfce4-panel.xml`, and a test pins that path.

## Considered options

- **An Install button for each app.** Rejected: the owner asked for the apps to be there. A password is the only thing the app asks for, and only when sudo needs one.
- **Hermes's `display.install`.** Rejected: its package list has no `mousepad` and no browser, and it needs the masked `display.install.sudo` request answered.
- **`hermes -p <profile> config path` for the dock's folder.** Not needed: `display.status` already carries the same folder as `profile_key`.
- **Restarting a running screen to refresh the dock.** Rejected: it would stop whatever the agent is doing on it.
- **Catching Ctrl+C and Ctrl+V on the screen.** Rejected: the screen's own apps need those keys, and the focus and pointer already mark when the owner switches between the two.
- **Plain `xclip -o` through `shell.exec`.** Rejected: Hermes keeps the last 4000 characters and masks credentials, so a long copy or a copied key comes out wrong.
- **Leaving out noVNC's cursor pseudo-encodings, with noVNC's dot for the owner's pointer.** Tried and dropped, as measured above.

## Supersedes

- **ADR 0039, in part.** Its decision "Not installed means a command, not an install button" still holds for the Bot Desktop's own packages. Its reason, that the app doesn't answer a masked sudo request, no longer holds for the apps this ADR adds: the app now asks for a sudo password itself, for its own ssh.
- **ADR 0078, in part.** On the Screen tab the fix for no browser is now installing pm's Chromium, and the command to copy is the fallback when that fails. Its considered option "An Install Chromium button. Not built." is built, with no button: `cli.exec` is the route it said was missing. Settings → Diagnostics keeps its Bot Desktop section and its command.

## Consequences

- The app now runs commands on the server through Hermes (`shell.exec`, `cli.exec`) as well as through ssh. Each one is fixed in the app; only the dock file's path comes from Hermes.
- `thunar` isn't installed. The dock shows Files only where it already is.
- The canonical session protocol's `shell.exec` runs only for a local session's composer, so an adapter for it (ADR 0174) would need another way to check and delete on the server.
- What is added is reported, not checked again after the package manager says it installed it.
- Copying out of the screen costs one `shell.exec` per 1967 bytes, each time the pointer leaves the screen while the owner holds it.
- On Windows the app doesn't copy or paste with the screen yet.
