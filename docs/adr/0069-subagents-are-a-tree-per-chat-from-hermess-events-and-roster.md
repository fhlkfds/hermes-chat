# Subagents are a tree per chat, built from Hermes's events and roster, with Steer and Stop for one at a time

Issue #95. A reply can hand parts of its work to subagents (Hermes's `delegate_task`), which can start subagents of their own. Until now the app showed none of that: the chat only showed the reply's own `delegate_task` tool call. Settings → Model only picks the model subagents run on. That is configuration, not what they are doing.

## Decisions

- **The contract is Hermes's own, at the deployed `f0d94882`.** While a subagent runs, Hermes sends `subagent.spawn_requested`, `.start`, `.progress`, `.tool`, `.thinking` and `.complete` on the chat's session. Each carries `subagent_id`, `parent_id`, `depth`, `goal`, `model`, `delegation_id`, `task_index`, `task_count` and `tool_count` (`tui_gateway/contracts/events.py` `SubagentEventPayload`, `tools/delegate_tool_progress.py`). `subagent.list {session_id}` returns the live roster and the background delegations that failed lately (`tui_gateway/methods_subagents.py`). Three more methods act on one subagent of the session: `subagent.tail` (the last 16 KB of its live transcript), `subagent.steer {subagent_id, text}` (`methods_session.py`) and `subagent.interrupt {subagent_id}`. Nothing is invented. A field Hermes doesn't send stays unknown.
- **One tree per chat, on this connection, in memory only** (`Chat.subagents`, `src/hermes/subagents.ts`). Each subagent is one record keyed by Hermes's `subagent_id`, in the order the app first heard of it. It holds its parent, depth, goal, model, state, last activity, tool count, its summary or error, and a log of its tool calls and reasoning. The tree is never saved on this computer, so a restart reads it again from Hermes.
- **Pure functions fold everything in.** `onSubagentEvent`, `onRoster`, `onLost` and `onUnchecked` take the tree and return the next one. Out-of-order events, repeats and a reconnect's roster all go through the same rules:
  - Once Hermes says how a subagent ended (`completed`, `failed`, `error`, `timeout`, `interrupted`), no later event or roster changes that.
  - **Ended** is the app's state for a subagent that ended without the app knowing how: Hermes's completion named no status it defines, or it ended unheard while the app was disconnected. It is final too, except that Hermes's own word on how it ended replaces it. **Unknown** is only for a parent the app knows from its child's events, until its own arrive.
  - What it last did only moves forward. Its tool count never goes down. Each last-activity line carries how many tool calls Hermes had counted by then (0 for the start, the roster's `tool_count` for its `last_tool`). A line with a lower count than the one shown doesn't replace it, so a late start or a tool call the roster already counted past stays in the log only. Once it ended, its end stays its last activity.
  - A request heard after the start doesn't move it back to queued.
  - Tool calls are placed by Hermes's per-subagent `tool_count`, each once, and the end stays last.
  - A subagent heard from before its parent makes an undescribed parent row, which its parent's own events fill in.
  - At most 200 activity rows per subagent and 100 subagents per chat. The oldest ended ones go first, and a running one is never dropped.
- **Kept out of the transcript.** Subagent events never become chat items. The panel above the composer shows them. A subagent opens to its own view, with its activity log and its output from `subagent.tail`.
- **Reconnects are labelled, not guessed.** When the connection drops, the tree keeps its last states and says it's disconnected. When the chat is next resumed, the app reads `subagent.list` once, which also covers a run started before the app opened.
  - A subagent the roster lists takes the roster's state, tool count, last tool and whether it takes steers.
  - A failed background delegation is matched to its subagent by `delegation_id` and `task_index`, only when both are known: the roster's live rows carry no task index. Otherwise it is added as its own row (`stored`, which has nothing to steer or stop), once however often the roster is read.
  - A running or queued subagent the roster leaves out ended without the app hearing how. It shows as **Ended**, "Ended while the app wasn't listening", never as finished. One the app heard from after it asked for the roster keeps its state, since the roster may have been made before it started.
  - A subagent first heard of from the roster, or part way through, is marked partial. Its view says that earlier activity isn't shown.
  - A Hermes without `subagent.list`, or a list that fails, leaves the tree as last heard and says why.
- **Answers that come too late are dropped.** A roster, an output read or a Steer or Stop answer is used only if the chat still has the same session on the same connection when it arrives. A drop rejects every request in flight.
- **Steer and Stop act on one subagent, named in full.** Each goes with the chat's own runtime session and that one `subagent_id`, nothing else. Hermes checks that the session asking started the subagent (`_owned_subagent_records`, `steer_subagent`). So a sibling, another chat, or another profile's subagent can't be reached.
  - Steer sits under a label with the subagent's goal and id. Its hint says only that subagent gets the words, after its current tool call.
  - Stop asks first. The question names the subagent and how many running subagents it started, since Hermes's interrupt reaches the target's own children (`interrupt_control.py`, `_active_children`). It also says that the chat's reply and the other subagents keep going.
  - The app reports what Hermes answered: `queued` or `rejected` for a steer, `found` for a stop. Its state changes only when Hermes's `subagent.complete` says it was stopped.
  - Both show only for a running or queued subagent with a Hermes id, and only while the chat is connected. They are refused, as writes, on a Hermes whose capability is unsupported.
- **Approvals stay the owner's.** At `f0d94882` a subagent never asks a client. Its dangerous commands are denied, or allowed when the profile sets `delegation.subagent_auto_approve` (`delegate_tool_config.py`). Subagents can't call `clarify`. So the only Approvals are the chat's own. The panel says when the chat's reply is waiting on one and has a **Go to it** button that moves focus to the card. The app answers nothing by itself.
- **A capability, `subagents`**, owns `subagent.list` and `subagent.tail` as reads and `subagent.steer` and `subagent.interrupt` as writes. Only a chat's own list can settle it, since the methods need a live session. Diagnostics shows it as unknown until then.

## Considered options

- **`subagent.roster`**, the app-wide feed of which conversations have running children. It names only counts per session, not the subagents. It could later light up chats in the list, but it adds nothing to one chat's tree.
- **Watching a child's own session (`child_session_id`) through `session.resume`.** That would reattach a second session to Hermes and mix the child's transcript into the app's chat handling. `subagent.tail` reads the same live transcript without side effects. Rejected.
- **Keeping the tree on this computer** so it survives a restart. Hermes already keeps the roster and failed delegations, and a kept copy would show states nobody can check. Rejected.
- **Showing the subagents inline in the transcript**, as tool calls. The issue asks for their output apart from the parent transcript, and a nested run would bury the reply.

## Consequences

- Hermes lets `subagent.tail`, `subagent.steer` and `subagent.interrupt` act only for the session that started a subagent. A chat resumed while its session is still live gets that same session back, so the controls keep working after a reconnect. This was seen live: a second connection resuming the chat got the same session id, and Hermes took its steer. If Hermes has let the session go and resumes the chat on a new one, `subagent.list` still shows the subagents (it follows the chat's lineage), but the controls are refused. The panel shows Hermes's refusal and doesn't predict it.
- Checked live against a throwaway Hermes `f0d94882` with a fake model that delegates (`src/hermes/subagents.live.test.ts`). The run covered three subagents and a nested one, a subagent the model refused failing while the others ran, the roster, the output tail, a steer that reached only its target, and a stop that ended its target and the subagent under it but not their sibling. On the wire, Hermes counts the reply's own subagents as depth 0. A steer reaches the subagent as a user message after its current tool result.
- Hermes relays a nested subagent's start and end to the chat, but not its tool calls or reasoning. Its parent's relay drops those (`delegate_tool_progress._normalize_event` has no entry for them). So a nested subagent's tool count and last tool come from `subagent.list`. The app reads the roster again whenever a subagent is opened or its output read again. While the app stays connected, a subagent the roster leaves out keeps its state, since its end comes as an event and the roster may have been made just before it started. Only after a drop does a missing one become Ended.
- `accepting_steer` comes only from `subagent.list`, so a subagent heard of only by events shows Steer. Hermes then answers `rejected` if it can't take it.
- Completed subagents are kept for the chat's whole time on this connection, up to the limit. A long chat with many delegations shows a long list. The panel stays collapsed, with a count, until opened.
- `subagent.thinking` only marks a subagent as running. Its text mixes Hermes's spinner lines (seen live) with the child's reasoning, and the two can't be told apart, so it isn't logged. The output tail has the child's own transcript.
